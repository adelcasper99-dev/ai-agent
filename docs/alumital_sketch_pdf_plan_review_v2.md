# مراجعة خطة v2 — التشخيص والحلول المعمارية صح، لكن التحول لـ Puppeteer فاتح باب مخاطر تشغيلية جديدة

## الأخبار الحلوة
التشخيص الجذري صح فعلاً — `librsvg` من غير HarfBuzz معروف إنه بيكسر تشكيل العربي، والحل بـ Chromium منطقي 100%. جدول القرارات (10 بنود / 6 بنود) قفل كل الـ "أو" الغامضة اللي كانت موجودة قبل كده. خطة الاختبار شاملة.

لكن التحول من `sharp` (مكتبة خفيفة) لـ **Puppeteer/Chromium الكامل** مش قرار مجاني — وده الحاجة اللي الخطة ماعالجتوش خالص:

## 1. تكلفة الموارد — الأخطر

السيرفر عندكم (HQ VPS) شغال عليه بالفعل: WhatsApp backend + Telephony voice service (LiveKit) + Admin dashboard + PostgreSQL. تشغيل Chromium instance كامل لكل صورة (وممكن توصل لـ 10 صور في المقايسة الواحدة) تكلفته RAM/CPU مختلفة تماماً عن `sharp` (اللي أصلاً كان خفيف وسريع).

**الأسئلة اللي الخطة محتاجة تجاوب عليها قبل التنفيذ:**
- هل هتفتحوا Chromium instance واحد وتستخدموه لكل الصور العشرة في المقايسة (Reuse) ولا هيتفتح ويتقفل instance جديد لكل صورة؟ لو التاني، ده هيبقى بطيء جداً وهيستهلك موارد فظيعة (كل فتح/قفل Chromium بياخد وقت وذاكرة).
- هل فيه أي queue/concurrency limit؟ لو اتنين عملاء طلبوا مقايسة في نفس الوقت، كل واحد بيفتح Chromium بتاعه، ده ممكن يطيّح السيرفر أو يبطئ باقي الخدمات (خصوصاً LiveKit اللي محتاج latency واطي للصوت الحي).

**التوصية:** استخدموا browser instance واحد persistent (يتفتح مرة عند بدء السيرفر ويتشارك بين كل الطلبات عبر tabs/pages منفصلة)، مش instance جديد لكل job. وحطوا حد أقصى لعدد الـ jobs المتزامنة.

## 2. الخطوط لازم تتأكد إنها متثبتة فعلياً على السيرفر

الخطة بتقول Chromium "يدعم خطوط Cairo/Noto" — ده صح بس بشرط إن الخطوط دي **متثبتة فعلاً كـ system fonts على الـ VPS نفسه**. لو السيرفر Linux minimal image (زي كتير VPS إعدادات افتراضية)، ممكن Chromium يشتغل صح تشكيلياً (الـ HarfBuzz موجود جوه Chromium نفسه) لكن يطلع مربعات فاضية (tofu) لغياب الخط. لازم خطوة تحقق صريحة: `fc-list | grep -i cairo` أو `noto` على السيرفر فعلياً قبل ما تعتبروا المشكلة اتقفلت، مش افتراض إنها موجودة.

## 3. متطلبات تشغيل Puppeteer على سيرفر (Headless deps)

لو Puppeteer ده أول استخدام له في المشروع (مش واضح من الخطة)، تشغيل Chromium headless على لينكس بيحتاج مكتبات نظام زيادة (`libnss3`, `libatk1.0-0`, `libgbm1`... إلخ) ومعظم الوقت محتاج `--no-sandbox` flag. لو المشروع مستخدم Puppeteer قبل كده في مكان تاني بنفس السيرفر يبقى مفيش مشكلة، لو لأ لازم تتأكدوا إن كل الـ dependencies دي متثبتة قبل الـ deploy، مش تكتشفوها وقت الفشل في الإنتاج.

## 4. معيار الاختبار رقم 2 غامض

"التأكد من توليد PNG سليم لكل منها" — "سليم" مش معيار قابل للقياس آلياً. لو الاختبار بيتأكد بس إن الملف اتولد من غير crash، ده مش كافي (ممكن يطلع PNG فاضي أو فيه مربعات tofu ولسه "يعدي" الاختبار). لو ينفع، ضيفوا فحص أبسط: تأكد إن حجم الملف الناتج فوق حد أدنى منطقي (byte size threshold) كمؤشر تقريبي، أو الأفضل مراجعة بصرية يدوية لعينة من كل نوع بند في خطوة النشر الحي (خطوة 5) بدل ما تعتمدوا بس على الاختبار الآلي لده تحديداً.
